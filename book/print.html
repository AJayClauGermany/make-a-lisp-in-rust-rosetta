Make-a-Lisp in Rust: a rosetta comparison

Introduction

This project compares Rust crates by making each of them do the same job inside a small Lisp interpreter.

The interpreter is Make-a-Lisp (mal), a language-agnostic guide that builds a Lisp in eleven numbered steps, with a test suite for each step. The guide splits the work into components with sharp boundaries: a reader, a printer, an environment, an evaluator, a core namespace and a REPL. Each of those is a job that several Rust crates can do, which makes each component a natural rosetta-rs-style comparison: one task, implemented once per crate, built and measured identically, presented in a table.

What you will find here

  • Methodology: what is measured, how, and what the columns mean.
  • The Make-a-Lisp steps: the ladder every implementation climbs, and which component each step exercises.
  • Architecture: the traits in mal-traits that all implementations are written against, and how the mal binary wires them together.
  • Benchmarking: how rows are timed, how runs are recorded under runs/, and how the results page is generated from them.
  • Trait notes: where the shared traits forced a row away from its crate's idioms, and the refinements proposed.
  • Components: one page per component with the candidate crates, the qualitative comparison table and notes on what the job demands.
  • Results: the measured tables from the most recent run.

Status

The first comparison rows are in place: 9 readers, 4 printers, 8 environments, the std evaluator and core namespace, and 3 line editors. Every new row reaches stepA_mal of the mal test suite (checked by cargo test), and every row except the line editors is timed on the results page. The evaluator and core namespace have only their std rows so far; the trait notes explain what blocks the other candidates.

Methodology

The method follows the rosetta-rs repositories such as parse-rosetta-rs and argparse-rosetta-rs.

One task, many crates

Each component of the interpreter is a task with a fixed interface, defined as a trait in mal-traits. A comparison row is a crate implementing that trait, in its own package under comparisons/<component>/<crate>/, depending on nothing but mal-traits and the crate(s) being compared.

Implementations are written the way a user of that crate would write them, not tuned for the benchmark. The question each row answers is "what is it like to do this job with this crate", not "how fast can this crate be made to go".

The baseline

Every component has a std row: the smallest implementation using only the standard library. It is the null row of the rosetta tables and the zero point for the overhead columns.

The mal binary currently links every row, so that the conformance tests and mal --reader nom can select any of them at run time. The planned binary-size column needs a mal built with only the baselines plus the one row being measured; that means putting each non-std row behind a cargo feature, which is not done yet.

Columns

Qualitative

Filled in by hand when a row is added, from the crate's documentation and the experience of writing the implementation. They differ per component; for example the reader table records parser type, where the action code lives and how the crate integrates (library, build script, proc macro).

Measured

Produced by cargo xtask bench and committed under runs/, one directory per run; the Results page is generated from the newest run. See Benchmarking for the mechanics.

The host (name, OS, architecture, CPU model and count), toolchain, commit and exact benchmark command of every run are recorded alongside the numbers, and the page says which run it was rendered from. Numbers from different hosts are presented side by side only with the host named; the change column between two runs is read as meaningful only when the hosts match.

Correctness

A row is only compared at the steps it passes the mal test suite for. The "step reached" column is therefore also a correctness statement, and an implementation that stops at step4_if_fn_do is reported as such rather than excluded.

The column is checked, not claimed: cargo test runs the upstream test files (vendored under crates/mal/tests/mal/) against every registered row with the same matching rules as mal's runtest.py, swapping that one row into an otherwise all-std interpreter, and fails if the step a row reaches differs from the step its Implementation states. Failures in the suite's optional (soft) sections are reported but do not count, as upstream.

Rows also run shared unit checks for their component (mal-testkit), and every reader must read every benchmark form to exactly the value the std reader produces, so the reader table never times an error path.

The Make-a-Lisp steps

The mal process guide builds the interpreter in eleven cumulative steps. Each has a test file in the mal repository, and mal_traits::Step names each one. The table shows which components a step first exercises, which is what decides where a new feature lands in this workspace.

stepnameaddscomponents exercised
0step0_replprompt, read a line, print it backline editor
1step1_read_printtokenising, parsing into values, printing themreader, printer
2step2_evalevaluating symbols and function callsevaluator
3step3_envdef!, let*, nested environmentsenv
4step4_if_fn_doif, do, fn*, the core namespaceevaluator, core
5step5_tcotail-call optimisationevaluator
6step6_fileread-string, slurp, eval, atoms, load-filecore, reader
7step7_quotequote, quasiquote, cons, concat, vecevaluator, reader
8step8_macrosdefmacro!, macro expansion, nth, first, restevaluator
9step9_trytry*/catch*, throw, apply, map, predicatesevaluator, core

Because the steps are cumulative, a row that reaches step 8 has passed the tests for steps 0 through 8. The Step enum is ordered the same way, so Step::Macros > Step::Quoting.

The workspace has a handful of permanent crates and a growing set of comparison crates.

mal-traits

Has no dependencies and contains no implementations. It defines one trait per component, each generic over the value type through an associated type so that value representation is itself something a row can vary:

traitmal modulejob
Readerreaderread_str: text to a value, or Empty for blank input
Printerprinterpr_str: value to text, readably or not
Envenvscoped bindings: child, set, get
EvaluatorstepN EVALevaluate a form in an environment
CoreNamespacecoreinstall the built-ins into an environment
LineEditorREPL inputread one line, optional history
Interpreterrepread, eval, print one line

Alongside the traits:

  • Component and Step enumerate the comparison axes. Component::slug() is the directory name under comparisons/; Step::name() is the mal test file name.
  • Implementation and CrateRef describe a table row: the crates used with exact versions, the highest step reached and one line of notes. Every comparison crate exports one Implementation constant so the tables are generated from the code rather than maintained by hand.
  • run_repl is the one shared piece of behaviour: the loop that reads a line, calls Interpreter::rep, prints the result or Error: ..., and stops at end of input. All interpreters share it so the measurements stay about the components.

mal-types

The traits leave the value type to each implementation, but a reader row can only feed a printer row, and the rows of one component can only be benchmarked on the same fixtures, if they agree on one. mal-types is that agreement: an Rc-based Value enum, MalError, mal equality, metadata and Value::apply, which lets the core namespace call closures without knowing the evaluator's environment type (closures store their environment type-erased). It has no dependencies. Evaluator rows that compare a different representation cannot use it; see Trait notes.

mal

The binary, plus the library the binary, the benchmarks and the tests share. It parses its flags by hand so argument parsing adds nothing to the size and build-time columns, ships the binary-level baselines (StdinLineEditor, EchoInterpreter), and keeps the registry that mal --list and the report generator read.

  • interpreter::Mal is the guide's rep: a reader, the evaluator and a printer around a top-level environment with the core namespace, the eval built-in, *ARGV*, *host-language* and the mal prelude (not, load-file, cond). ReadPrint is step1: read and print only.
  • select builds an interpreter from row names: mal --reader nom runs the nom reader with std everywhere else. Only one of reader, printer, env, eval and core may differ from std at a time, so the number of monomorphised interpreters grows with the number of rows rather than their product. --line-editor is chosen separately, and --read-print composes with any reader or printer row.
  • tests/conformance.rs runs the vendored mal test suite (tests/mal/) against every registered row through the binary and fails if a row does not reach exactly the step it claims. step0_repl runs only for the echo evaluator and step1_read_print in --read-print mode, because those files test the shape of their own step.

Comparison crates are timed from here too: benches/components.rs is one line per implementation, calling the matching harness function. Criterion, mal-bench and the test dependencies are dev-dependencies only, so they never reach the binary.

mal-bench and xtask

mal-bench holds the fixed workloads (corpus) and one generic Criterion benchmark per component trait, each recording under the group <component>/<implementation> so results can be joined back to the registry. xtask is the runner: cargo xtask bench records a run as runs/<id>/results.json, cargo xtask report renders the newest run and the registry into docs/src/results.md, and cargo xtask compare diffs two runs. Their third-party dependencies (Criterion, serde) never reach the mal binary. See Benchmarking.

Comparison crates

Each depends on mal-traits, mal-types and the crate under test, implements one trait, and exports its Implementation. See Contributing.

Benchmarking

Every implementation is timed on the same fixed inputs with Criterion, each run is committed as data under runs/, and the Results page is generated from the newest run. Nothing on that page is typed by hand.

The pieces

piecewherejob
workloadscrates/mal-bench/src/corpus.rsthe fixed mal forms, the evaluation PROGRAMS, the REPL session and symbol lists every row is measured on

The harness is a dev-dependency of mal and the runner a separate crate, so neither reaches the mal binary. The comparison crates do: the binary currently links every row so any of them can be selected at run time (see the methodology for what that means for the planned binary-size column).

Interpreter benchmarks run rep on every corpus form, and check once, before timing, that each succeeds, so an error path is never what gets measured. Interpreters that evaluate run corpus::BINDINGS first, which defines the free symbols the forms mention (a, counter, swap-and-reset!).

Adding an implementation to the benchmarks

After the row exists and is registered (see Contributing), add one line to the function for its component in crates/mal/benches/components.rs:

#![allow(unused)]
fn main() {
fn readers(c: &mut Criterion) {
    mal_bench::reader(c, &reader_nom::IMPLEMENTATION, reader_nom::NomReader::default);
}
}

Each harness function takes the row's Implementation constant, which fixes the Criterion group name to <component>/<name> so the report can join the numbers back to the registry, and a constructor. Components whose value type belongs to the implementation (printer, environment, evaluator, core namespace) also take the fixtures to run on, typically the corpus forms parsed with the row's own reader:

#![allow(unused)]
fn main() {
mal_bench::env(c, &env_im::IMPLEMENTATION, env_im::ImEnv::default, |i| Value::Int(i as i64));
mal_bench::printer(c, &printer_std::IMPLEMENTATION, &printer_std::StdPrinter, &values);
mal_bench::evaluator(c, &eval_rc::IMPLEMENTATION, eval_rc::setup, &forms);
mal_bench::core_namespace(c, &core_std::IMPLEMENTATION, core_std::Core::default, Env::default);
}

Environment rows are timed twice: mal_bench::env on the trait methods, and mal_bench::evaluator running the PROGRAMS workloads (recursive fib, a tail-call loop, closures through map) with the std evaluator on that environment, recorded under the environment's own group as env/<name>/eval/<program>. The second is what an interpreter actually does with an environment.

Line editors are not timed: their run time is the terminal's, and the comparison for that component is binary-size overhead. They still appear on the results page as not measured, because the page lists every registered implementation.

Recording a run

cargo xtask bench                       # record under runs/, regenerate the page
cargo xtask bench -- eval/              # pass a Criterion filter through
cargo xtask bench --host desk --no-report
cargo xtask report                      # regenerate docs/src/results.md
cargo xtask report --check              # what CI runs
cargo xtask compare <run-a> <run-b>     # side-by-side change in mean

cargo xtask bench clears target/criterion/ first so the run contains exactly what that invocation measured, runs cargo bench -p mal, reads Criterion's benchmark.json and estimates.json for every benchmark, and writes runs/<yyyymmdd>-<hhmmss>-<host>/results.json. Run ids sort chronologically, so "the newest run" is the last directory.

Record on a quiet machine, commit the run directory together with the regenerated page, and say which machine it was in the pull request. A run from a different host is still worth committing; the page names the host and marks the vs previous column as only meaningful between runs from the same one.

What is not measured yet

The methodology also calls for binary-size overhead, debug build time and run time on the mal test suite per row. Those are whole-binary measurements rather than Criterion benchmarks; they will be added to cargo xtask bench as further sections of the run file once the first comparison crates exist to be built in and out of the binary.

Trait notes

Every row is written the way a user of its crate would write it. Where the traits in mal-traits (or the shared value type in mal-types) forced a row away from that, the friction is recorded here, with the rows it affects, so the traits can be refined and the rows updated together afterwards.

The traits themselves were changed in one place only while the first rows were written; everything else below is worked around in the rows and listed as a candidate refinement.

Changes made

changewhy
run_repl accepts I: Interpreter + ?SizedThe binary chooses its rows at run time and holds the interpreter as Box<dyn Interpreter<Error = _>>. Backwards compatible.
New crate mal-types (not a trait change)The traits are generic over Value, so rows only interoperate if they agree on one. mal-types is that agreement: an Rc-based Value, MalError, equality and function application. Dependency-free, like mal-traits.
New --read-print mode (wiring, not a trait change)step1_read_print.mal expects symbols to print back unevaluated, so reader and printer rows are checked against it without an evaluator.

Ordered roughly by how many rows they would simplify.

Notes by component

Shared value type

  1. No shared value type. Each trait has its own associated Value, so without an agreed type a reader row could not feed a printer row, and rows of one component could not be benchmarked on the same fixtures. Solved with mal-types (above). The cost: evaluators that compare memory management (Arc, arenas, gc) cannot use it and would have to bring a reader and printer of their own, which is why the evaluator table has only the std row so far. Refinement 8.
  2. Closures and the environment type. A closure captures an environment, but the value type is shared by every environment row. The std evaluator stores the environment as Rc<dyn Any> with an apply function pointer and downcasts it again. The alternatives were worse: making Value generic over the environment puts a phantom parameter on every reader and printer, and forces every environment row to be a non-generic newtype to break the recursive type.
  3. Value::map_from_pairs returns MalError. Readers then need a From<MalError> conversion that flattens it to a string, and because MalError::Thrown holds an Rc, it is not Send + Sync, so winnow cannot carry it as a ContextError cause and peg can only report a static label. A small Send + Sync map error would fix both.
  4. Strings are copied twice. Every reader that unescapes builds a String and then copies it into an Rc<str>. This is inherent to Rc<str> (the reference counts live in the same allocation), so not a trait issue, but it is part of every reader row's cost.

Reader

  1. The EOF requirement is a message convention. The mal test suite matches .*(EOF|end of input|unbalanced).*. Of the crates, only lalrpop (UnrecognizedEof) and chumsky (found end of input) say so on their own. nom and winnow get it from a hand-written Display; pest and peg decide "ran out of input" by checking whether the error position is the input length (pest also when it is at a ", since it reports failures in atomic rules at the rule's start); logos maps an unmatched character to "unterminated string" because that is the only way it can happen; regex re-checks string tokens because the guide's tokenizer accepts an unterminated string. logos and regex copied the std row's error enum wholesale. Refinement 1.
  2. Reader::Error cannot borrow the input. winnow's ParseError, chumsky's Rich<'src>, lalrpop's ParseError tokens and pest's errors all borrow, so every row converts to an owned error at the boundary (winnow loses its caret rendering, lalrpop allocates a string per expected token, pest's error is boxed because it is large). Refinement 1 (owned, with an offset) or a generic associated Error<'a>.
  3. "First form only, ignore the rest" fights grammar entry rules. pest needs SOI ~ (form | EOI) without a trailing EOI; peg's pub rule must consume everything, so the entry rule ends in [_]* and walks the rest of the input on every read; lalrpop's LR parser must reach EOF, so the grammar accepts <Form> Token* and has an extra token for unterminated strings in the trailing input; winnow's parse needs terminated(form, rest). Refinement 2.
  4. &mut self and Default are mostly unused. Seven readers are unit structs. lalrpop keeps its generated parser (which compiles a regex set on construction) and needs a manual Debug. chumsky cannot keep its parser at all: its type borrows the input lifetime, so read_str rebuilds the grammar on every call, and the chumsky row's timings include that.
  5. Overflow and bad maps need hard failures. In nom, winnow and peg a failed integer conversion backtracks, and the token would silently read as a symbol; each needs a cut, a checkpoint reset or a !integer() guard.
  6. Reader macros must not fall back to symbols. ~, @ and ^ are symbol characters inside a symbol (a~b) but start a reader macro at the beginning of a form. A combinator grammar without a cut tries the macro, fails when no form follows, and backtracks into reading ~ as a symbol: chumsky did exactly that until its symbol rule excluded those first characters, as the pest, lalrpop and logos grammars do.
  7. No depth limit in the trait. Every recursive-descent row overflows the stack on deep enough nesting, aborting the process, and the trait has no way to report "too deep" as an error. How deep differs a lot. Reading an unclosed run of ( in a debug build of the binary (so only the reader recurses), nom aborts at about 340 levels, winnow 1,700, peg 2,050, logos 2,700, regex 5,000 and std 5,300, while chumsky (stacker), pest (its stack guard) and lalrpop (an explicit LR stack) read 200,000. Release builds use smaller frames and get further. The printer rows recurse too, so printing a deep enough value overflows whichever reader built it. A max_depth setting or an Error case for it would turn the crash into a reported error.
  8. nom's escaped_transform misreports a trailing backslash. It reports "abc\ at the start of the string body rather than as running out of input, and rejects an empty body. The row uses fold_many0 over literal runs and escapes instead, as nom's own string example does.

Printer

  1. &mut String output. The trait appends to a String, which rules out the small-string candidates on the printer page (compact_str, smol_str) as output buffers and writing straight to io::Write. Refinement 7. ryu is not a row because Value has no floats.

Environment

  1. set takes &str. Every binding allocates an owned key, including every parameter of every function call, although the value already holds the symbol as an Rc<str>. hashbrown's entry_ref avoids the allocation only when rebinding. Refinement 5.
  2. Persistent maps cannot be used as persistent maps. The idiomatic environment on imbl or rpds gives each child scope a structurally shared snapshot of its parent, so lookups hit one map. Env::set through a parent must be visible to children created before it (recursive def! after fn* captured the scope relies on it), which snapshots break. So both rows keep the scope chain and a RefCell, and the persistent map is just a map. Refinement 6.
  3. No constructor in the trait. The wiring and the benchmarks need E: Default. Refinement 12.

Evaluator

  1. eval(&mut self) versus re-entry. eval, apply, map, swap! and macro expansion all call back into the evaluator from inside a built-in or closure, so the evaluator has to be stateless and Clone, and the eval built-in clones it per call. Refinement 4.
  2. DEBUG-EVAL cannot be implemented. The optional tests that bind DEBUG-EVAL expect the evaluator to print each form, and the evaluator has no printer. These are soft failures (17 across steps 3, 7 and 8) in every row.
  3. Reference cycles leak. Every closure that captures the scope it is defined in (every recursive def!) and the eval built-in, which captures the top-level environment, form Rc cycles. This is the cost of the std row's memory-management strategy rather than a trait issue, and what a tracing-GC row would be measured against.

Core namespace

  1. The core needs other components. read-string needs a reader, pr-str/str/prn/println a printer, and eval, apply, map and swap! the evaluator; install only receives the environment. The std row is generic over a reader and a printer, calls functions through Value::apply, and eval is installed by the wiring. Refinement 3.
  2. readline cannot use the line-editor row. It reads standard input directly.
  3. Representation is fixed. The numeric candidates (num-bigint, rug) need a different number type in Value, and the core is the only row that would change it. Refinement 10. Until then the core table has only the std row.
  4. The benchmark only times install. Timing the built-ins themselves would make a second core row worth comparing.

Line editor

  1. "Show the prompt" when piped. rustyline reads piped input itself but stops printing the prompt, and the newline at end of input, so the row writes both; it still applies backspace characters in piped lines, which the other rows pass through unchanged. reedline cannot run without a terminal at all; the row reads piped input with std::io, as nushell does, so the step column for reedline is reached through that fallback. The conformance tests pipe input (runtest.py --no-pty); upstream runtest.py uses a pseudo-terminal by default, where reedline sends a cursor query before every line that the runner does not cope with.
  2. History. add_history returns (), so rustyline's error is dropped; reedline records history itself, so the call is a no-op. Neither can save a history file without a lifecycle hook. Refinement 11.

Interpreter and wiring

  1. Run-time selection multiplies code. Every row is generic, so every combination the binary can run is a monomorphised copy. The binary allows one row to differ from std at a time, which keeps the copies linear.
  2. Rendered errors. run_repl prints Error: {e} with Display, which cannot print a thrown mal value with the printer row, so the wiring's error type is a pre-rendered String. Refinement 9.

Dependency findings

Not trait issues, but found while writing the rows and relevant to the MSRV (1.85) and the version column:

  • lalrpop 0.23 needs Rust 1.86; the row uses 0.22.2.
  • reedline 0.52 needs 1.95; the resolver chose 0.49.0.
  • rustyline 18 and 19 depend on home 0.5.12, which needs 1.88 without rustyline declaring a rust-version; the row uses 17.0.2 with home pinned to 0.5.11 in Cargo.lock.
  • psm 0.1.27 and later (used by pest's stack guard and chumsky's stacker) build-depend on ar_archive_writer, which uses let chains (1.88); Cargo.lock pins psm 0.1.26.

A plain cargo update can undo the last two pins; cargo +1.85 check --workspace --all-targets (the MSRV job) catches it.

Components

The interpreter is split along the lines of the mal guide. Each component is a trait in mal-traits, a directory under comparisons/, and a page here with its candidate crates and qualitative table.

Reader

Trait: mal_traits::Reader. Directory: comparisons/reader/.

The reader tokenises source text on the mal token grammar and builds lists, vectors, hash-maps, strings, keywords, numbers and symbols, including the reader macros ', `, ~, ~@, @ and ^. It is the component with the richest field of candidate crates, and the one most directly comparable to parse-rosetta-rs.

What the job demands

  • Unbalanced delimiters and bad string escapes must be reported as errors, not panics; the test suite checks the messages loosely.
  • Blank and comment-only input is ReadOutcome::Empty, not an error.
  • Only the first top-level form is read; trailing input is ignored.

Notes from the rows

Every grammar crate had to be bent to read one form and ignore the rest, and only lalrpop and chumsky report running out of input in words the test suite accepts on their own; the others decide it from the error position. chumsky's parser type borrows the input, so it is rebuilt on every read_str call and its timings include that. See Trait notes for the details and proposed refinements.

Printer

Trait: mal_traits::Printer. Directory: comparisons/printer/.

The printer renders values back to mal source text, either readably (strings quoted and escaped so the reader can read them back) or raw, for str and println. It is a small job, which makes it a good place to compare formatting and number-to-string crates on overhead alone.

What the job demands

  • Exact escaping of ", \ and newline in readable mode.
  • Sequences joined by a single space; hash-maps printed as alternating keys and values.
  • Function values print as #<function>.

Environment

Trait: mal_traits::Env. Directory: comparisons/env/.

An environment maps symbols to values and chains to an outer environment for lexical scoping. Closures capture environments, so environments are shared and cheap to clone. This component compares map crates and persistent data-structure crates, and is sensitive to allocation count and lookup speed on short string keys.

What the job demands

  • child() creates an empty scope that falls back to its parent.
  • set() binds in the innermost scope only.
  • get() walks outward; the evaluator turns None into a 'x' not found error.

How the rows are measured

Each row is timed twice: the trait methods on their own (set, local and outer lookups, a miss, child), and the std evaluator running the PROGRAMS workloads on that environment, which is where binding parameters and walking scopes show up in practice.

The persistent maps (imbl, the maintained fork of im, and rpds) cannot be used the way they are meant to be: Env::set through a parent has to be visible to children created before it, which rules out giving each child a structurally shared snapshot. Both rows keep the scope chain and a RefCell like the others. See Trait notes.

Evaluator

Trait: mal_traits::Evaluator. Directory: comparisons/eval/.

The evaluator is the guide's EVAL: special forms, function application, tail-call optimisation, quasiquote expansion, macro expansion and try*/catch*. It fixes the value representation, so this is the component that compares memory-management strategies rather than any one crate category: reference counting, arenas and tracing garbage collectors.

What the job demands

  • step5_tco requires the evaluator to loop rather than recurse for if, do, let* and function application in tail position.
  • Closures capture an environment; atoms are mutable; both force some form of shared ownership.
  • Deep recursion in the test suite (sum-to, fib) is where value representation shows up in run time.

Status

The std row is generic over the environment row, so it also drives the environment comparison. The other candidates change the value representation, which every reader and printer row is written against (mal-types), so each would need its own reader and printer until readers can build any representation; see Trait notes.

Core namespace

Trait: mal_traits::CoreNamespace. Directory: comparisons/core/.

The core namespace installs the built-in functions: arithmetic and comparison, list and vector operations, strings, hash-maps, atoms, slurp, time-ms and the printing functions. It is where supporting crates for numbers, strings, hashing and time enter the interpreter.

What the job demands

  • symbols() must list exactly what install() binds; the test suite's coverage is checked against it.
  • Arithmetic in the test suite is integer only, but the guide allows richer numeric towers, which is what the numeric candidates explore.
  • read-string, pr-str, str, prn and println use the reader and printer rows the interpreter was built with; eval is installed by the interpreter, since it needs the evaluator.

Status

Only the std row exists: the numeric candidates need a number type other than the shared Value::Int(i64), and the benchmark only times install. See Trait notes.

Line editor

Trait: mal_traits::LineEditor. Directory: comparisons/line-editor/.

The line editor shows the user> prompt and reads a line for the REPL, optionally with editing and history. The guide suggests a readline library from step0_repl onward and a readline built-in at stepA_mal. This is the component where binary-size overhead is most visible, since a line editor is a large dependency relative to the interpreter.

What the job demands

  • Ok(None) at end of input, so the REPL exits cleanly on Ctrl-D.
  • Must work when standard input is not a terminal. Upstream runtest.py runs implementations on a pseudo-terminal by default (--no-pty pipes); this repository's conformance tests pipe input, so they check the non-terminal path.

Notes from the rows

rustyline reads piped input itself but stops printing the prompt and the newline at end of input, so the row prints them; it still applies backspace characters in piped lines, unlike the other rows. reedline needs a terminal, so the row reads piped input with std::io, and its step column is reached through that fallback; on a pseudo-terminal it sends a cursor query before every line, which upstream runtest.py does not cope with. See Trait notes.

Contributing

The point of this repository is the comparison tables, so the most useful contribution is a new row: another crate doing one of the component jobs.

Adding a crate to a comparison

  1. Pick the component the crate is a candidate for. The six components and their directory names are in mal_traits::Component: reader, printer, env, eval, core, line-editor.

  2. Create the crate at comparisons/<component>/<crate>/, named <component>-<crate> (for example comparisons/reader/nom/ with package name reader-nom). Depend on mal-traits by path:

    [package]
name = "reader-nom"
version.workspace = true
edition.workspace = true
license.workspace = true
publish.workspace = true

[dependencies]
mal-traits = { path = "../../../crates/mal-traits" }
mal-types = { path = "../../../crates/mal-types" }
nom = "8"

[dev-dependencies]
mal-testkit = { path = "../../../crates/mal-testkit" }

[lints]
workspace = true

  3. Add it to the workspace in the root Cargo.toml members list. Cargo rejects globs that match nothing, so members are listed explicitly.

  4. Implement the trait for that component (mal_traits::Reader, Printer, Env, Evaluator, CoreNamespace or LineEditor) over mal_types::Value, and export one pub const IMPLEMENTATION: mal_traits::Implementation describing it: the crates used with exact versions (a test checks them against Cargo.lock), the highest mal step it passes, and one line of notes for the table. Readers, printers and environments call the shared checks from a test: mal_testkit::check_reader(NomReader::default).

  5. Register it in crates/mal/src/registry.rs so mal --list and the generated tables see it, add it as a dependency of crates/mal, and add a line to build in crates/mal/src/select.rs so mal --reader nom runs it. cargo test -p mal --test conformance then runs the mal test suite against it and fails unless it reaches exactly the step it claims; MAL_CONFORMANCE=reader/nom runs just that row.

    If the trait made you write something a user of the crate would not, keep it and add a note to docs/src/trait-notes.md.

  6. Add a page at docs/src/components/<component>.md if the component does not have one yet, and a row in that component's table.

  7. Benchmark it with one line in crates/mal/benches/components.rs, in the function for its component:

    #![allow(unused)]
fn main() {
mal_bench::reader(c, &reader_nom::IMPLEMENTATION, reader_nom::NomReader::default);
}

    Then cargo xtask bench records a run under runs/ and regenerates docs/src/results.md; commit both. See the benchmarking page for the components that also take fixtures, and for recording runs.

Keep implementations idiomatic for the crate being compared rather than optimal for the benchmark. The comparison is about what it is like to use the crate for this job; a row nobody would write in practice is not informative.

What gets measured

See the methodology page. In short, per implementation: Criterion timings of its trait methods on fixed workloads (recorded today), and, planned, binary-size overhead against the std baseline, debug build time, run time on the mal test suite for the highest step reached, and the crate's download count at the time of the run.

Checks

CI runs the following; please run them before pushing.

cargo fmt --all -- --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo test -p mal --benches        # runs every benchmark once, as a smoke test
cargo xtask report --check         # docs/src/results.md matches the newest run
RUSTDOCFLAGS="-D warnings" cargo doc --workspace --no-deps
cargo deny check
