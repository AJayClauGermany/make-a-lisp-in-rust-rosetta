Make-a-Lisp in Rust: a rosetta comparison

Stacks: combining rows

The component tables measure one row at a time against std. A real interpreter is one reader, one printer, one environment, one evaluator and one core namespace together, and the compiler optimises them together: every row is generic, so each combination is its own monomorphised copy of the interpreter, built with fat LTO. A reader can be inlined into the read-string built-in; an environment's lookup can be folded into the evaluator's loop; two rows that allocate the same way can share warm allocator caches. So a combination can be faster, or slower, than its rows suggest on their own. A stack is such a combination. This page explains how to build, check and measure stacks.

Generic rows

Readers, printers and environments are plain types. Evaluators and core namespaces are generic over the rows they call (StdEvaluator<E>, StdCore<E, R, P>), so their rows are families: a marker type with a generic associated type that picks the member for the other rows of the stack (EvalRow::For<E>, CoreRow::For<E, R, P>). A new evaluator or core row adds a two-line marker next to StdEvalRow / StdCoreRow.

Choosing stacks: the spec

One spec syntax is used by the benchmarks (MAL_STACKS), the consistency test (MAL_STACKS), the conformance test (MAL_CONFORMANCE_STACKS) and cargo xtask bench --stacks. Components are separated by spaces or ; and rows by ,. A component left out stays std. * means every row of that component that reaches stepA_mal.

sweep                        std, then every row swapped into it alone
reader=nom,winnow env=*      2 readers × 13 environments
printer=* ; env=rustc-hash   every printer on the rustc-hash environment
reader=* printer=* env=*     every combination of those three
all                          every combination of every component

To vary one component and hold the rest fixed at something other than std, name the fixed rows once and use * for the one that varies: reader=logos env=rustc-hash printer=*.

The benchmarks also add the std stack and the stack for each non-std row on its own, because the interaction of a combination is measured against them.

Default build versus matrix

A default build compiles only the stacks with at most one non-std row: one copy of the interpreter per row, a little over thirty. mal --reader nom works; mal --reader nom --env fnv explains that it needs the matrix feature. With --features matrix every combination is compiled (about nine hundred today). That costs about 12 s extra in a debug build, but about ten minutes (on 4 CPUs) for the stack benchmarks: release builds use fat LTO and one codegen unit, which is what lets the optimiser see across rows. So it is off unless asked for:

cargo run -p mal --features matrix -- --reader winnow --printer itoa --env rapidhash
cargo test -p mal --features matrix --test stacks          # every combination vs std
MAL_STACKS='reader=nom,winnow env=*' cargo test -p mal --features matrix --test stacks
MAL_CONFORMANCE_STACKS='reader=nom printer=*' cargo test -p mal --features matrix --test conformance

Measuring

cargo xtask bench --stacks sweep                    # no matrix needed
cargo xtask bench --stacks 'reader=* env=*'         # adds --features matrix itself
cargo xtask bench --stacks all -- --warm-up-time 1 --measurement-time 2

Each stack is timed on four workloads (the three PROGRAMS through rep, and the REPL session), recorded as stack/<label>/<workload>. The label lists the non-std rows, e.g. stack/reader=nom,env=fnv, or is std. At Criterion's defaults that is about 30 seconds a stack. The sweep is about 30 stacks; reader=* env=* is about 140; all is about 860, so it is only practical with shorter Criterion times as above. A stack run is recorded like any other. The results page takes its component tables from the newest run that measured components and its stacks section from the newest run that measured stacks, so the two kinds of run do not hide each other.

Reading the results

For each stack the results page shows:

  • ratio: the geometric mean, over the workloads, of the stack's time divided by the std stack's time;
  • predicted: for a stack with several non-std rows, the product of the ratios of the stacks that swap in each of those rows alone. This is what the combination would cost if the rows did not affect each other;
  • interaction: ratio divided by predicted. Below 1× the rows do better together than their separate results predict, above 1× worse. Values within 5% are marked as noise.

An interaction is the thing to look for. "The best reader plus the best environment" is only the best stack if the interaction is near 1×. When it is not, the combination is the finding. A typical case would be a reader whose symbols share allocations with an environment's keys, or two rows that each inline well alone but together push the evaluator loop past an inlining threshold.
