Make-a-Lisp in Rust: a rosetta comparison

Compare Rust crates by making each of them do the same job inside a Lisp interpreter.

Make-a-Lisp (mal) describes a small Lisp as a ladder of eleven steps and a handful of components: a reader, a printer, an environment, an evaluator, a core namespace and a REPL. Each component is a job that several Rust crates can do, so each one becomes a comparison in the spirit of rosetta-rs: the same task, implemented once per crate, measured the same way, with the results in a table.

This repository holds the shared traits, the runner, the comparison implementations and the published results.

Status: first comparison rows in place: 9 readers, 4 printers, 8 environments, the std evaluator and core namespace, and 3 line editors, each checked against the upstream mal test suite and benchmarked. Where the traits forced crates away from their idioms is recorded in Trait notes, ahead of refining the traits.

Layout

Path What it is
crates/mal-traits The component traits every implementation is written against. No dependencies.
crates/mal-types The shared Rc-based Value and MalError that rows of different components agree on. No dependencies.
crates/mal-testkit Unit checks every reader, printer and environment row runs (dev-dependency only).
crates/mal The mal binary: a stepA interpreter assembled from rows, --<component> <name> to swap one in, and mal --list. Its benches/components.rs is the list of what gets benchmarked, and tests/conformance.rs runs the mal test suite against every row.
crates/mal-bench The benchmark harness: fixed workloads and one generic Criterion benchmark per component trait.
xtask/ cargo xtask bench records a run under runs/; cargo xtask report renders the newest run into the results page.
comparisons/ One crate per <component>/<crate> pair. Each exports an Implementation record and depends only on mal-traits, mal-types and the crate it compares.
docs/ The mdBook behind the documentation site: methodology, per-component pages, results.
oranda.json oranda configuration for the site, built and published from main by .github/workflows/web.yml.
runs/ One results.json per recorded benchmark run (host, toolchain, commit, statistics), committed so results are reproducible.

Components

Each table lists the crates compared for one component. The std row is the dependency-free baseline everything else is compared against; step reached is checked by cargo test against the upstream mal test suite. Timings are on the results page; the component pages on the documentation site have the candidates not yet implemented.

Results

Every implementation is timed with Criterion on the same fixed workloads. cargo xtask bench records a run as runs/<id>/results.json, and the results page on the documentation site is generated from the newest run together with the implementation registry, so it always shows every registered row, measured or not. Above each table, charts drawn from the same numbers show each implementation's time relative to std, overall and per workload. CI fails if the page is stale. The binary-size, build-time and test-suite columns of the methodology are not measured yet; see the benchmarking page.

Running

cargo run -p mal                      # start the REPL (all std rows)
cargo run -p mal -- --reader nom      # the same with one row swapped in
cargo run -p mal -- --list            # list the implementations available to compare
cargo test --workspace                # includes the mal test suite for every row
cargo xtask bench                     # benchmark, record under runs/, regenerate docs/src/results.md
cargo xtask report --check            # verify the results page matches the newest run

To preview the documentation site locally, install oranda and run oranda dev in the repository root.
